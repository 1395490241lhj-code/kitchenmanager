# AI 增量开发与测试工作流

本文件是 Kitchen Manager 中 Agent 的增量开发、测试选择、失败处理和对话切换规则。它补充而不替代：

- `AGENTS.md`：Agent 入口、项目边界和按任务读取路径；
- `CLAUDE.md`：Claude Code 入口；
- `TESTING_RULES.md`：各平台的具体命令、测试矩阵和环境安全要求；
- `PROJECT_WORKFLOW.md`：单次开发任务的通用生命周期。

当规则涉及具体测试命令时，以 `TESTING_RULES.md` 为准；当规则涉及是否扩大验证范围、是否重试或是否切换对话时，以本文件为准。仓库代码、配置、迁移和可执行测试仍然优先于文档描述。

## 1. 修改前检查

每次修改前：

1. 查看 `git status --short`、当前分支和 `git diff`，确认不会覆盖与任务无关的工作；
2. 阅读受影响的文件、直接相关测试和必要的项目文档；
3. 说明修改涉及的表面和影响范围：PWA、iOS、服务端、数据库、认证、同步、共享数据契约、测试或文档；
4. 先确定最小充分验证，再开始编辑。不要把“证明安全”理解成默认运行全部测试。

修改完成后至少检查 `git diff --check` 和最终 diff。涉及缓存、配置、密钥、迁移、备份、feature flag 或远端环境时，还要按现有项目规则做专项检查。

## 2. 增量测试决策

测试范围按实际影响从小到大升级。除非满足第 3 节的升级条件，否则保持在最小充分范围。

### 2.1 纯 UI、文案、布局、颜色、图标或 Preview 修改

- 只编译受影响的 target（适用于存在 target 的客户端）；
- 检查相关 Preview、模拟器页面，或必要的快照/视觉回归；
- 不运行完整单元测试或完整 UI 测试。

若改动同时触及导航、共享组件、状态转换、持久化或网络行为，则按对应行为规则扩大范围。

### 2.2 单个页面、ViewModel、Service 或独立模块修改

- 只运行与改动直接相关的测试类或测试方法；
- 做必要的语法检查、编译或局部运行检查；
- 不运行无关模块测试。

### 2.3 SwiftData、迁移、认证、同步、网络层或跨模块修改

- 运行受影响模块的聚焦测试；
- 根据契约运行必要的集成测试、迁移/RLS/网络安全验证或手动流程；
- 只有存在明确的全局影响时才扩大到完整测试，例如共享持久化基础设施、核心模型、公共路由/协议或跨多个客户端的契约。

具体命令和 iOS/PWA/服务端矩阵见 `TESTING_RULES.md`，不要在本文件重复维护命令列表。

## 3. 何时运行完整测试

### 3.1 完整单元测试

只有在以下情况运行完整单元测试：

- 一个完整功能阶段结束；
- 准备提交或合并 PR；
- 修改共享基础设施或核心数据模型；
- 用户明确要求。

### 3.2 完整 UI 测试

只有在以下情况运行完整 UI 测试：

- 准备发布；
- 完成重大用户流程改动；
- 用户明确要求。

如果没有触发这些条件，最终报告必须明确列出跳过的完整测试，并说明它们与当前影响范围无关或留待功能阶段/发布门禁执行。

## 4. 测试输出、失败和重试

- 测试成功时只保留简短摘要：命令、范围、通过结果和必要的耗时/环境信息；不要读取或输出完整日志。
- 测试失败时只读取失败测试及错误附近的必要日志；避免把整份构建或测试日志放入上下文。
- 代码或测试断言失败时，以同一个 failing test、test class、target 或同一根因为计算单位。Agent 最多自动进行一次代码修复并重新运行相关测试；如果仍然失败，停止继续改代码并报告当前失败、已尝试的修复、可能根因和剩余风险。
- 环境或工具问题（例如 simulator destination 错误、simulator 未启动、临时缓存/DerivedData 问题、package resolution 临时错误、命令参数或工作目录错误）在不修改业务代码的前提下，最多进行两次有限重试；仍失败后停止并报告。
- 修复后出现不同错误，但仍属于同一个 failing test、target 或同一修改范围时，不产生新的无限重试预算。
- 不要通过削弱断言、关闭安全检查、跳过失败测试或扩大无关测试来“取得绿色”。
- 远端 smoke、数据库迁移、真实用户数据、部署和 feature flag 变更仍需明确授权；它们不是普通的本地增量测试。

## 5. 文档和报告节奏

- 小修改不要自动更新全部项目文档；文档在其职责所属的功能阶段结束时集中更新。
- 测试策略或命令矩阵变化更新 `TESTING_RULES.md`；Agent 行为和增量决策更新本文件；当前状态更新 `PROJECT_STATUS.md`；稳定架构更新 `PROJECT_GUIDE.zh.md`（必要时同步英文摘要）。
- 不要把同一条规则复制到多个入口文件。入口文件只负责指向和要求遵循本工作流。
- 最终报告遵循 `AGENTS.md` 的格式，并明确：运行了什么、跳过了什么、为什么跳过、是否有远端写入/密钥/环境影响。

## 6. 适合开启新对话的时机

Agent 应在下列情况主动提醒用户，当前任务适合下一步开启新对话：

- 一个完整功能已经完成并通过相关验证；
- 即将切换到明显不同的功能模块；
- 当前对话积累了大量日志、截图或多轮修复记录；
- Agent 开始重复读取背景文件，或旧上下文已经影响判断；
- PR 已完成、分支已合并，或项目进入新的开发阶段。

同一功能的小幅连续调整不应频繁建议切换对话。提醒时附上一段可直接复制的新对话启动上下文，至少包含：

- 当前分支和工作树状态；
- 已完成内容；
- 已运行的聚焦测试；
- 尚未运行的完整单元/UI 测试；
- 下一项任务建议；
- 新对话必须阅读的项目文档。

建议模板：

```text
新对话启动上下文
- 分支/工作树：<branch>；<clean 或未提交文件>
- 已完成：<功能或修复>
- 已验证：<聚焦命令和结果>
- 尚未运行：<完整单元/UI 测试及原因>
- 下一步：<建议任务>
- 必读文档：AGENTS.md、PROJECT_STATUS.md、docs/AI_WORKFLOW.md、<相关契约/测试文档>
```

## 7. 文档类修改的验证

普通 Markdown、Agent 指令和开发文档修改，默认不运行完整 `npm test`、完整 iOS 单元测试或完整 UI 测试。只执行与文档一致性相关的轻量验证，例如：

```bash
git diff --check
```

还应按需要执行路径和链接检查、Markdown 结构检查、交叉引用检查，以及对被文档实际解析的 JSON/config 文件进行校验。

只有以下情况才运行相关项目测试：

1. 文档被测试、脚本或构建流程实际解析；
2. 修改同时涉及 `test/`、`scripts/`、配置生成或 semantic guard；
3. 用户明确要求。

轻量验证不能证明应用行为正确；最终报告必须说明实际验证范围，以及未运行的完整测试和原因。
